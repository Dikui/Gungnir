实现用户在需求文档、任务单或任务单目录（如 `.scratch/<feature>/issues/`）中描述的工作。一份小需求或一张任务单按只有一张任务单的批次处理。

## 1. 排出批次

读取全部任务单，按 `Blocked by` 排出批次：前置任务都已完成的任务单进入同一批。同一批中预计会修改相同文件的任务单，拆到前后两批。

完成条件：每张未完成的任务单都属于一个批次；已向用户列出批次。

## 2. 实现本批任务单

本批每张任务单派一个子代理（只有一张时也派），各自在独立的 worktree 和分支中实现；任务书只含该任务单、相关 ADR 和下面的实现规则，不含其他任务单的进展。不能派子代理时，当前会话按编号逐张实现。

每张任务单的实现规则：

- 通过 Skill 工具加载 `/tdd`，尽可能在预先约定的可替换位置（seam）上按它开发。
- 定期运行类型检查和受影响的单个测试，不运行完整测试套件。
- 任务单与它写明为准的文档冲突时，按文档做，并在报告中指出冲突。
- 涉及界面时，交付前在浏览器里逐个检查任务单列出的场景；没列时至少检查宽度 1440 和 390、浅色和深色主题、项目支持的每种语言、长文本。每个场景截图，报告附截图路径。没有浏览器工具时在报告中写明未检查，不声称通过。
- 删除、重命名、精简类任务，按任务单列出的关键词搜索确认无残留，并确认保留项仍在，报告附搜索命令和结果。
- 实现完成后，通过 Skill 工具加载 `/local-test`，按它测试受影响范围，并沉淀值得保留的测试。用户催促时也必须运行；可以缩小补测试的范围，筛选和沉淀不能省略。
- 然后通过 Skill 工具加载 `/diff-review`，审查这张任务单的改动。跳过审查时，在报告中说明。
- 提交到所在分支。报告附上实际运行的命令和结果。

完成条件：本批每张任务单都已提交，并有命令和结果。

## 3. 合并本批

子代理的分支按任务单编号逐个合并到当前分支。每合并一个，重跑该任务单报告中的测试命令。合并冲突或测试失败时停下，报告分支和失败输出，不合并后续分支。

全部合并后，删除本批子代理的 worktree 和分支。然后回到第 2 步处理下一批。

完成条件：本批全部合并且测试通过，临时 worktree 和分支已删除；或已停下并报告。

## 4. 验收

按 Gungnir 工作流的“验收单”格式请用户验收，停下等待。验证证据列出每张任务单的提交、运行过的命令和结果、沉淀的测试；本轮没有运行过的检查，不说通过。完整测试套件由仓库的 pre-push 钩子在版本号前两位变化时运行，或由 CI、用户运行；本轮没有运行时写明。项目 `AGENTS.md` 写了试用方式的，附上试用命令。

验收通过后不再逐项确认：把当前分支合入默认分支，用 `/safe-push` 推送（视为已授权），再按项目 `AGENTS.md` 写的方式部署。合并冲突、扫描阻断或部署失败时停下报告。验收不通过时，按意见修改并重新测试，再出一份验收单，只列差异。
