# 版本号确认

在 `SKILL.md` 第 7 步读取。按以下顺序完成；每个询问点都等待用户回答。这里的确认不代替提交和推送确认。

## 1. 定位版本文件

先读 `docs/agents/push-rules.md` 的“版本文件”一节。有明确路径和字段时直接使用，不再探索确认。该节写明无版本文件时，仍按下文“找不到版本文件”询问。路径不存在、字段含糊或版本来自动态计算时，列出问题并请用户指定，不能猜测。

没有该节或没有规则文件时，探索项目结构和常见版本位置：

- `package.json` 的 `version`，以及对应 lock 文件中本包自身的版本字段。
- `.claude-plugin/plugin.json` 的 `version`。
- `pyproject.toml` 的项目版本、`Cargo.toml` 的包版本及对应 lock 中本包条目。
- `VERSION` 等独立版本文件。

列表不是固定白名单。依据项目结构区分本项目、工作区子包和第三方依赖；列出候选路径、字段及各自用途，请用户确认本次版本范围。多个独立包不假定共用一个版本，先确认要升级哪些包，再分别执行后续确认。找不到版本文件时，明确告知并询问：“请指定版本文件，或选择本次不升版本。”选择不升即记录原因，返回主流程；用户指定后再读取验证。

规则文件存在但缺少该节时，在版本文件确认后询问是否写入“版本文件”一节；确认后按 [push-rules-template.md](push-rules-template.md) 的自然语言格式写入。另行确认该规则改动是否并入本次提交；若加入，逐路径暂存并重跑主流程第 3–5 步。不要连带暂存规则文件的未确认改动。主流程第 2 步已选择“暂不创建”时，不再询问创建规则文件，本次只用确认的版本范围。

## 2. 核对当前版本及已有升级

读取每个已确认字段的当前值。以本次拟提交的值为准：已暂存文件读取索引，否则读取 HEAD；新文件读取经用户确认的工作区内容。同时比较工作区、索引和 HEAD，记录已存在的版本改动及其他改动，避免覆盖或混入。值不一致时列出路径、字段和值，停下请用户确定基准；确定基准不等于获准改文件，仍须完成具体版本选择。用户已有的暂存升级也须明确确认保持或更改。

有 upstream 时使用其远端引用；推送目标与 upstream 不同时使用主流程第 1 步确定的目标远端分支。无 upstream 时检查该目标远端分支是否存在。读取远端对应字段，与本地 HEAD 及拟提交值比较，并检查主流程第 3 步列出的每个未推送提交的版本差异，不能只看净变化而漏掉中途升级或回退。

已有版本变化时说明“未推送提交中已从 A 升到 B”，列出涉及的提交；回退、多次变化或各文件不一致时如实列出。询问保持现状还是改为其他版本。保持现状须同时展示并确认具体版本 B，作为本次不再升级的决定；选择其他版本再进入候选选择。仅暂存的版本变化也明确展示并确认，不默认重复升级。

目标远端分支或旧字段不存在时，说明无法比较的范围；不要声称已经检查了远端版本。远端引用过时或获取失败，沿用主流程第 1 步说明的检查边界。

## 3. 给出候选并等待确认

对语义化版本，基于已确认的当前版本列出 patch、minor、major 三个具体版本号，以及“不升版本”“自定义”。例如当前为 `1.2.3`，候选为 `1.2.4`、`1.3.0`、`2.0.0`。根据暂存内容和所有未推送提交给出一个推荐及一句理由；修复通常推荐 patch，兼容功能通常推荐 minor，不兼容变更通常推荐 major。

有预发布标识或构建元数据时，明确三个候选如何处理这些后缀，不能静默删改；需维持预发布序列时请用户给出具体版本。不符合语义化版本时说明情况，请用户直接给出版本号或选择不升，不套用三种增量。

只有用户明确选定一个具体版本号或明确选择不升才算确认。用户选择与已展示具体版本唯一对应的 patch、minor、major 选项也算选定；“自定义”仍须给出版本值。“随便”“你看着办”不算确认，重新询问，不能代选。

用户给出的版本号不高于当前版本，或格式与现有版本不一致时，说明具体问题并再次确认该具体值和意图；再次明确确认前不得修改。确认保持原值时记为不升，不制造空版本提交。

## 4. 修改、暂存与重扫

选择不升时不修改任何版本字段，记录原因，返回主流程。选择新版本时：

1. 先检查每个版本文件在工作区和索引中的差异。含与版本无关且未经确认的改动时，停下列出差异，请用户处理或明确其提交范围；此时不修改、不暂存这些文件，不自动还原用户内容。用户处理后重新核对范围。
2. 只改已确认文件中表示本项目自身版本的字段，保持其他内容和格式。
   lock 文件只改本包自身条目；例如 `package-lock.json` 的顶层 `version` 和 `packages[""]` 中的 `version`，旧格式按其实际结构确认。
   依赖版本即使与旧版本相同也不改。不运行 `npm install` 等重新生成 lock 的命令。
3. 不改 CHANGELOG、历史说明或其他出现旧版本号的位置。对各旧版本执行 `git grep -nF <旧版本号>`，列出剩余位置及用途，交给用户判断，不自动修改。该命令未命中时退出码 1 表示无结果；新文件等未跟踪内容另行核对，不能误报为已经搜索过。
4. 展示实际版本差异，逐路径暂存确认范围；原先仅推送已有提交时也如此，版本改动单独构成本次提交。有新的未确认改动时停下，不能整文件连带暂存。
5. 返回主流程重新执行第 3–5 步，按第 6 步解决阻断并重新取得警告决定。版本相关 lock 变更也须审查，不能自动放行。把版本决定和最终差异带入第 8 步的提交确认。
