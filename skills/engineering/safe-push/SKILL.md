# 检查、提交与推送

先检查、再一次性确认、最后提交推送。任何一步失败时停下，报告原因。范围、规则或 Git 状态变化后重新扫描，不沿用旧的放行决定。

## 授权与停下条件

用户原话里说了“推送”“提交推送”等，或用户验收通过后由 `/implement` 调用，就视为已授权本次提交和推送；说“提交”只授权提交。已授权的部分不再单独确认，只在出现下列情况时停下，并在一屏汇总里一次问完：

- 扫描出阻断。
- 警告尚未决定修复还是放行。
- 有待判断或非核心文件。
- 找不到版本文件，或版本文件候选不止一个（见第 4 步）。
- 推送目标有多个候选、与项目规则或 upstream 不一致，或需要强推、改写历史。
- 仓库处于中途操作（merge、rebase、cherry-pick）或分离 HEAD。

未授权的部分（如只说了“提交”时的推送）照常询问。

## 1. 前置检查与规则

在仓库根目录确认没有中途操作，读取当前分支、upstream、`git remote -v`，确定目标 remote 和远端分支。默认分支每次用 remote 引用核实（无缓存时 `git ls-remote --symref <remote> HEAD`）。有 upstream 时列出 `git log @{upstream}..HEAD`，没有时用 `git log HEAD --not --remotes`。展示 URL 时隐藏凭据和查询参数。

读取 `docs/agents/push-rules.md` 和 `docs/agents/layout.md`（“提交=否”的路径记为非核心）。没有规则文件时，按 [push-rules-template.md](push-rules-template.md) 起草，放进汇总里询问“写入”或“暂不创建”；暂不创建时只用内置规则继续。

## 2. 确定范围

暂存区非空时以 `git diff --cached` 为范围；为空时用 `git status --short` 列出改动，只取与当前任务有关的文件。每个文件按 [RULES.md](RULES.md) 的“核心内容”判为核心、非核心或待判断；后两种进汇总由用户决定，未决定前不提交。同一文件混有两类改动时请用户先拆开。

逐路径暂存，用 `--` 隔开选项，不得 `git add -A` 或 `git add .`。所有未推送提交都在检查范围内，更早提交中的问题即使 HEAD 已删除也要处理。

## 3. 扫描与审查

读取 [RULES.md](RULES.md)，在项目根目录执行（`<skill-dir>` 是本技能的安装目录）：

```sh
bash <skill-dir>/scripts/scan.sh --staged --unpushed --remote <remote> --target <远端分支>
```

输出每行五列 TSV：`block|warn`、类别、文件、行号、脱敏说明。退出码 `0` 无阻断、`1` 有阻断、`2` 扫描错误；`2` 不能当成通过。

代理对十三类逐项补审，重点是第 2、5、9 类，以及脚本误报。本地 tracker 下，`.scratch/*/` 中任务单全部关闭、但 `spec.md` 和 `map.md` 顶部都没有 `ADR review: done` 的功能，列为警告，建议按 `docs/agents/layout.md` 的“收尾检查”处理。

有问题时提出具体修法（移出暂存区、加入 `.gitignore`、改用环境变量、换成假数据），用户同意后执行，再重扫，直到无阻断、无扫描错误、警告都有决定。本地提交有问题需改写历史时，先说明影响并确认。已推送的密钥必须轮换，改写历史撤不回泄露。密钥内容一律打码，最多保留前四字符。

## 4. 版本号

只在当前分支和目标都是默认分支时处理版本号；其他分支记为“未升版本：非默认分支”。

版本文件按 `push-rules.md` 的“版本文件”一节；没有时探索 `package.json`、`.claude-plugin/plugin.json`、`pyproject.toml`、`Cargo.toml` 等，把候选放进汇总请用户确认。比较远端、HEAD 和未推送提交中的版本值；已经升过时说明“未推送提交中已从 A 升到 B”，不重复升级。

默认只升修订号（patch，如 1.2.3 → 1.2.4），不用询问。用户原话里给了具体版本号、说了“不升”，或明确要求升次版本（minor）或主版本（major）时，按用户说的做。代理不自行升 minor 或 major。只改本项目自身的版本字段（lock 文件只改本包条目），不改依赖、CHANGELOG 和历史说明，不打 tag，不发布。

## 5. 汇总

扫描和版本都处理完后，出一屏汇总：

- 提交的文件列表（含版本文件）和完整提交信息（按项目约定起草，升版本时写“版本升到 X”；对草稿做第 12 类检查）。
- 推送目标：remote、脱敏 URL、`本地分支 → 远端分支`、待推送提交。
- 版本变化 `A → B` 或未升原因。
- 放行的警告及理由。
- 停下条件中出现的待决定项，编号列出，每项附推荐。

没有待决定项且已授权时，直接进入第 6 步；有待决定项时等用户一次答复。

## 6. 提交与推送

提交前核对暂存区与汇总一致。commit 不用 `--no-verify`；hook 失败时报告原因，修复后重扫。推送使用显式 refspec 并关闭自动带标签：

```sh
git -c push.followTags=false push <remote> HEAD:refs/heads/<远端分支>
```

无 upstream 时加 `-u`。不主动强推；用户明确要求时只用 `--force-with-lease`。被拒绝时停下报告，不换 remote、不重试强推。

## 7. 结果

报告提交 hash、分支、目标、推送成功与否、版本变化或未升原因、放行的警告。成功时核实远端引用与 HEAD 一致，查询失败标记未核实。
