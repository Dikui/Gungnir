# 检查、提交与推送

按下面十步执行。扫描只读仓库；配置写入、问题修复、版本号、提交和推送各有确认点。任何一步失败时停在该步，报告原因。规则配置、Git 状态或待提交内容变化后，重新确定范围并扫描，不能沿用旧的放行决定。

## 1. 前置检查

确认 `git rev-parse --show-toplevel` 成功，切到仓库根目录。

用 `git rev-parse --git-path <名称>` 定位下面的状态文件或目录；任一个存在即停止，要求先完成或退出正在进行的操作。

```text
MERGE_HEAD
CHERRY_PICK_HEAD
REBASE_HEAD
rebase-merge
rebase-apply
```

读取当前分支、`@{upstream}`、`git remote -v`、分支的 `remote` 和 `merge` 配置。分离 HEAD 时停止并请用户确定分支。

确定目标 remote、推送 URL（`git remote get-url --push <remote>`，检查多 URL 配置）和远端分支。

多个候选或无 remote 时先询问，不自行猜测。展示 URL 前隐藏用户名密码、token 和查询参数。

有 upstream 时列出 `git log @{upstream}..HEAD`；没有时用 `git log HEAD --not --remotes`，不要把“没有 upstream”当成“没有未推送提交”。空仓库可先提交。远端引用可能过时，检查上次获取时间；需要刷新时仅对已确定且无凭据输出的 remote 获取引用。获取失败时说明检查边界，不能声称检查了最新远端。

完成条件：仓库无中途操作，分支、目标和未推送提交已明确。

## 2. 项目规则

读取 `docs/agents/push-rules.md`。存在时，同时遵循自然语言说明和机器规则。

不存在时先探索 `.gitignore`、测试夹具或假数据目录、remote 列表、默认分支引用、仓库说明中的受保护分支和最近提交约定。

默认分支引用无缓存时，在条件允许时执行：

```sh
git ls-remote --symref <remote> HEAD
```

Git 不能推断服务器全部保护规则；缺失时向用户确认。

按 [push-rules-template.md](push-rules-template.md) 生成符合发现的草稿，列出事实与待确认项，展示完整草稿。询问“确认写入”或“暂不创建”；只有确认后才写入。暂不创建时只用内置规则继续，下次运行仍询问。新配置文件是否入本次提交另行确定。

完成条件：已读规则，或已确认创建/暂不创建；不要为了配置自动放行测试假密钥。

## 3. 确定范围

暂存区非空时，以 `git diff --cached` 为提交范围。工作区中的其他改动不自动加入。暂存区为空时，用 `git status --short` 列出修改及未跟踪文件，分为与当前任务有关、无关、待判断三组；用户确认具体文件后逐路径暂存。不得执行 `git add -A` 或 `git add .`。支持空格和中文路径，逐个引用路径，使用 `--` 隔开选项。

未推送的每一个 commit 都在范围内，包括新增行、文件列表和提交信息。更早提交中的问题即使在 HEAD 删除也要处理。暂存区只含已确认内容；记录 HEAD、索引差异及未推送提交列表，供确认前核对。

## 4. 扫描与审查

首次扫描前读取 [RULES.md](RULES.md)，了解十三类的级别、规则语法及脚本边界。在项目根目录执行本技能的脚本（`<skill-dir>` 是安装后的技能目录，不是项目目录）：

```sh
bash <skill-dir>/scripts/scan.sh --staged --unpushed --remote <remote> --target <远端分支>
```

不指定范围时默认两者都扫。

`--staged` 只扫暂存区；`--unpushed` 只扫未推送历史；`--base <rev>` 覆盖历史基准，检查 `<rev>..HEAD` 的每个提交，不能用较新的基准隐藏本应推送的提交。

无 upstream 时默认排除所有 remote 引用。`--remote`、`--target` 用于第 13 类提示；明确准备强推时另加 `--force`。分支名与推送风险提示始终检查。

标准输出每行五列 TSV：`block|warn`、类别编号、文件、行号、脱敏说明。行号 `0` 表示文件属性、分支或提交信息；提交以 `(commit:<hash>)` 标识。脚本不输出源码片段，密钥内容全部隐藏。标准错误是无原文的诊断。退出码 `0` 无阻断，`1` 有阻断，`2` 扫描错误；`2` 不能当成通过。

若 `command -v gitleaks` 成功，先看本机 `gitleaks --help` 确定版本用法，启用完全打码（如支持则 `--redact=100`），覆盖暂存区及同一批历史提交，合并结果并去重。不要仅扫描 HEAD 文件而漏掉早期提交。工具不支持安全输出或所需范围时，报告该工具检查未完成并由代理补审，不能将未脱敏输出存入报告。未安装就跳过，不要求安装。

代理对范围内十三类逐项审查，重点是第 2、5、9 类，文件整体换行/格式变化、子模块、个人用户名、历史中的忽略规则，以及脚本和 gitleaks 的误报。机器无命中不代表通过人工审查。

完成条件：两个范围均已检查，工具错误已解决，十三类都有结论。

## 5. 报告

按“阻断”“警告”分组，每项写类别、`文件:行号`、原因、建议。提交问题附 hash。密钥内容一律打码，最多保留前四字符；命令、URL、hook 和工具错误也适用。第 13 类标记为推送前需单独确认。说明哪些判断来自代理及哪些范围未能检查。

## 6. 处理并重新扫描

提出具体方案，如移出暂存区、加入 `.gitignore`、读取环境变量或替换成假数据。用户确认后执行；不要覆盖其无关修改。加入 `.gitignore` 不会自动移除已跟踪内容，移出本次范围后仍需检查历史。

阻断必须解决。警告逐项或明确列出的批次由用户选择修复/放行，记录理由及对应内容。假密钥的豁免必须限定路径和内容，用户确认规则后重新扫描。

已有本地提交有问题时，展示 `git reset --soft <安全基准>` 或修订 commit 等历史改写方案及影响；确认后才执行。已推送内容中的密钥不能靠改写历史撤回泄露，必须轮换（作废并更换）；明确告知，技能不自动处置这种情况。

处理后重跑步骤 3–5，直到无阻断、无扫描错误，全部警告已有决定。修复改动涉及已暂存文件时，只暂存用户确认的修复内容。

## 7. 确认版本号

每次推送都询问是否升版本号，包括暂存区为空、只推送已有提交或没有版本文件的项目。进入本步时读取 [VERSION.md](VERSION.md)，按其中流程定位版本文件、核对当前值与未推送的版本变化，并给出候选和推荐理由。

只有用户明确选定具体版本号或明确选择不升，才能完成本步。版本文件、基准或回复不明确时停下询问，不能代选。获准的版本改动并入本次提交；原先无待提交内容时，它们单独构成本次提交。

按确认范围修改并逐路径暂存后，重新执行第 3–5 步；有问题则回到第 6 步。范围、版本值或规则改变后重新核对相关确认，不能把重扫当成再次升版本。不得创建或推送 git tag，不运行 `npm publish` 等发布命令。

完成条件：版本决定及理由已记录；新增的暂存内容已重扫，无阻断、无扫描错误，全部警告已有决定。

## 8. 提交

按项目约定起草提交信息；选定新版本时写明版本变化，例如“版本升到 X”。对草稿执行第 12 类人工检查（脚本只能检查已有提交）。展示最终文件列表（含版本文件）和完整的安全提交信息；核对范围没有变化，用户确认后 commit。不用 `--no-verify`；hook 失败时报告脱敏原因，修复后重新扫描和确认，不绕过。没有待提交内容时明确说明，继续检查既有待推送提交。

## 9. 推送

提交后再次扫描未推送历史，核对 HEAD 和暂存区状态。

展示 remote 名称和脱敏后的 push URL、`本地分支 → 远端分支`、待推送 commit 的 hash 与安全摘要。

检查 upstream 是否与目标一致、目标是否是默认或受保护分支、是否强推；按第 13 类逐条单独列出，用户确认目标、列表及这些风险后才执行显式 refspec 的 push：

```sh
git -c push.followTags=false push <remote> HEAD:refs/heads/<远端分支>
```

无 upstream 时在用户确认建立对应关系后加 `-u`。不主动强推；只有用户明确要求时使用 `--force-with-lease`，说明 lease 的基准引用，不能改用 `--force`。拒绝或失败时停下报告，不能换 remote 或自动重试强推。

显式关闭自动跟随标签，避免项目或全局的 `push.followTags` 配置带出标签。

## 10. 结果

报告提交 hash、分支、目标和推送成功/失败，以及版本变化 `A → B`，或“未升版本”及原因（用户选择不升、无版本文件、保持已有版本等）。保持未推送提交中已有升级时，另列该变化，说明本次没有再次升版本。成功时核实远端对应引用与 HEAD 一致（查询失败则标记未核实）。一并列出放行的警告及理由、gitleaks 是否运行、未完成检查。扫描、版本决定、提交、推送和结果核实均有结论后才完成。
