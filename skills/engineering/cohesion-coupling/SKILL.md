# 内聚与耦合

输入：用户指定的 module 或目录。

## 开始前

- 读取已有的 `GLOSSARY.md` 和 `docs/adr/` 中的相关 ADR。
- 把 ADR 中记录的决策和理由作为证据。
- 职责分析前读取 [codebase-design](../codebase-design/SKILL.md)，术语沿用其中的 module、interface、seam 等。
- 只给诊断结论和建议。
- 不修改任何文件。临时改动与还原规则（共同规则 6）不适用。
- 不向项目安装依赖，不修改 `package.json` 等清单文件。
- 展示或记录命令、输出或环境信息前，将秘密值替换为 `<REDACTED>`。

## 执行规则

- 按顺序执行步骤。
- 完成条件未满足时，不进入下一步。
- 跳过某步时说明理由。
- 需要用户确认时，提出问题。停下等待回答。收到确认前不按假设继续。
- 无法交互时，输出待确认问题和已完成的部分。以 `未完成：等待用户确认` 结束。
- 能从仓库、文档或工具查到的事实，由代理自行查证。
- 决策交由用户确认。
- 证据不足的条目标为 `待确认`。写明缺少的证据。
- 在报告中写明覆盖范围和未覆盖部分。有未覆盖部分时标为 `部分完成`。
- 不得用“未发现问题”代替覆盖说明。不得据此给出整体通过结论。
- 结论是线索，以证据为准。不为假设中的需求拆分 module。

## 范围确定

使用用户指定的 module 或目录。未指定时，用 `git log` 找改动最频繁的区域，请用户确认范围。
完成条件：分析范围已确定；未指定时已收到用户确认。

## 步骤

### 1. 职责表
每个 module 用一句话写职责。写不出一句，或需用“并且”连接两件无关的事时，列为低内聚候选。
同一职责分散在多个 module 时，列为职责分散候选。
完成条件：范围内每个 module 都有职责描述，或注明无法描述的原因。
### 2. 依赖图
分析 import 和调用关系。优先用项目已有工具，如 madge、dependency-cruiser、`go list`；没有时用 grep 估算并注明精度。
找出循环依赖、被大量依赖且经常改动的 module、依赖过多的 module。
检查违反分层方向的依赖，以及访问其他 module 内部细节的地方。
完成条件：使用的工具或方法及其精度已写明；范围内每个 module 的依赖都已分析。
### 3. 变更耦合
统计最近 200 个提交中，经常在同一提交里修改的跨 module 文件对。经常同改但无显式依赖时，列为隐性耦合线索。
历史不足 200 个提交时，注明实际数量。
完成条件：统计命令和前若干对结果已给出。
### 4. 坏味道
读取并对照 [diff-review 坏味道表](../diff-review/SKILL.md)。
重点看 Shotgun Surgery、Divergent Change、Feature Envy。
同时检查 Message Chains、Middle Man。用“可能存在”措辞。
完成条件：重点坏味道均已检查；线索附位置和证据，未覆盖部分已说明。
### 5. 建议
每个问题给出重组方向：合并、拆分、移动职责或反转依赖。按收益和成本排序。
需要设计 interface 时，建议用户调用 `/codebase-design`。
完成条件：每个问题都有重组方向和收益、成本说明；按产出模板报告，证据不足项和未覆盖部分已标明。

## 产出模板

```
## 范围
<…>；状态：完成 / 部分完成（未分析：<module 与原因>）

## 职责表
| module | 职责 | 标记（低内聚/职责分散/—） |

## 依赖问题
| 问题类型 | 涉及 module | 证据（文件、import 行） |
工具与精度：<…>

## 变更耦合
统计命令：<…>
| 文件对 | 同改次数 | 是否有显式依赖 |

## 可能存在的坏味道
| 坏味道 | 位置 | 证据 |

## 建议（按收益/成本排序）
| 问题 | 重组方向 | 收益 | 成本 |

## 依赖图（可选，Mermaid）
```
