用户已提供一份需求文档。这份需求文档应有关联的任务单，说明如何实现它。

用户应已提供issue tracker。若没有，请告诉用户运行 `/setup-matt-pocock-skills`。

目标是在一个**集成分支**上实现整份需求文档，并按issue tracker关闭工作的方式完成每张任务单。

任务单不是步骤列表，而是带有阻塞关系的**任务依赖图**。因此，始终有一组已可领取的任务单，构成**待执行集合**。

与子代理的双向通信应保持精简。主要通过**上下文指针**通信：指向需求文档、任务单、调研笔记和之前的提交。不要重复指针中已有的信息。

尽可能在后台运行**实施子代理**，以提高并发度。

## 步骤

1. 阅读需求文档和任务单，理解任务依赖图。

2. （可选）使用**探索子代理**完成任务单所需的探索，包括相关代码文件或外部文档。确保探索子代理能保存文件：它应将 Markdown 笔记保存到仓库之外、所有后续子代理都可访问的目录中。这样**实施子代理**就能专注于实现，而非探索。

3. 创建集成分支。若issue tracker通过 PR 关闭工作，或用户要求 PR，在步骤 5 首次合并后创建草稿 PR（没有领先 main 的提交时无法创建 PR），并将其标记为关闭需求文档和任务单。

4. 使用**实施子代理**实现每张任务单，每个子代理使用自己的 worktree 和分支。每个实施子代理：
   - 开始前确认其 worktree 基于集成分支；若不是，将其重置到集成分支；
   - 通过 Skill 工具调用 `tdd` 来实现任务单；
   - 汇报完成前，将集成分支的最新提交合并到自己的分支。

5. 一个**实施子代理**完成后，使用**合并子代理**将其工作合并到集成分支。

6. 若可用任务单的**待执行集合**发生变化，启动更多**实施子代理**处理新任务单，以提高并发度。

7. 所有任务单完成后，通过 Skill 工具对集成分支调用 `code-review`。由一个**实施子代理**修复代码审查提出的所有问题。

8. 若已有草稿 PR，将其标记为可供审查。否则，按issue tracker关闭工作的方式完成每张任务单，并汇报集成分支。

9. 清理所有**实施子代理**的 worktree。
