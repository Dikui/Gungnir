# 追目标

用于能用一条命令测出结果的目标，例如延迟、准确率、评测分数、测试通过率。目标测不出来时，告诉用户本技能不适用，建议先用 `/grill-me` 再用 `/implement`，然后停止。

用户只在第 1 步确认约定、第 4 步验收时参与。两步之间自行决定下一步，不汇报进度，不问是否继续。

开始前读用户偏好：全局偏好在 `~/.gungnir/preferences.md`，项目偏好在仓库 `AGENTS.md` 的“偏好”一节，冲突时以项目为准。读取已有的 `GLOSSARY.md` 和相关 ADR。

## 1. 定目标约定

先确定目标：

- 用户给的是需求：目标或达标线含糊时，通过 Skill 工具加载 `/grill-me` 澄清。
- 用户给的是失败案例或问题现象：逐个读案例，按原因归类，把案例最多的一类写成目标。其余类别列给用户，由用户决定是否纳入。

把约定写入 `.scratch/<feature>/pursue.md`（项目有 `docs/agents/layout.md` 时以它为准）：

- **目标**：一句话，不含实现方式。
- **评测命令**：能直接运行，输出一个数值或通过与失败的计数。没有现成命令时，写明要新建的评测和案例来源，用户确认后先建评测。
- **达标线**：指标方向（越大越好或越小越好）和达标的数值。
- **运行次数**：每次评测运行几次，默认 3 次，取中位数。单次评测很贵时与用户商定次数。
- **预算**：第 3 步最多几轮，默认 10 轮。
- **授权范围**：可以修改的目录，能否安装依赖，能否调用外部服务。用户没说的，按最小范围写：只改仓库内文件，不装依赖，不调用收费或有副作用的外部服务。合入默认分支、推送、部署和删除数据不能写入授权范围。

运行 `git status --porcelain`。有未提交改动时，在约定里写明，并问用户先提交还是连同这些改动一起作为基线。

请用户确认约定，停下等待。

完成条件：用户确认了约定。

## 2. 测基线

1. 记录当前提交的 SHA，作为基线 SHA。
2. 按约定的运行次数运行评测。记录每次结果、中位数和噪声。噪声是最大值减最小值；各次结果相同时记为 0。
3. 评测跑不通时修评测命令。修不好时停下报告。
4. 基线已经达标时，进入第 4 步。

基线测完后，评测命令、已有案例和达标线不再修改。发现评测本身有错（算错、案例标错）时，停下报告，由用户决定。

完成条件：`pursue.md` 的进展记录里有基线 SHA、各次结果、中位数和噪声。

## 3. 循环

**改善**：中位数朝达标方向变化，且变化量大于噪声。**比较基准**：最近一次保留的评测结果，开始时是基线。

每轮按顺序做：

1. 读 `pursue.md` 的约定和进展记录。
2. 按下表选一个功能区，只做一件事。
3. 改了代码或评测案例时，按约定的运行次数重跑评测。
4. 有改善时提交这轮改动，结果成为新的比较基准。没有改善时撤回这轮改动。
5. 在进展记录末尾追加：第几轮、功能区、做了什么、评测结果、保留（附提交 SHA）或撤回、下一轮去哪和理由。

| 当前情况 | 功能区 | 做什么 |
| --- | --- | --- |
| 没达标，不知道差在哪 | 分析与归因 | 读失败案例或剖析数据，按原因归类，找出占比最大的原因 |
| 知道差在哪，不知道怎么改 | 调研与方案 | 通过 Skill 工具加载 `/research` 查一手来源；列出候选方案，之后每轮从同一比较基准出发试一个 |
| 知道怎么改 | 实现与实验 | 按下面的实现规则改一处 |
| 分析中发现评测没有覆盖的失败类型 | 数据与评测 | 新增案例，按下面的评测规则 |
| 连续两次代码改动都没有改善 | 调研与方案 | 通过 Skill 工具加载 `/first-principles` 重新推导方向 |

实现规则：

- 一轮只改一处：一个原因对应一处改动。结果变化时能说清来自哪处改动。
- 改变行为的改动，通过 Skill 工具加载 `/tdd` 实现。只影响指标、不改变行为的改动（如性能优化）直接改。
- 改完后通过 Skill 工具加载 `/local-test`，测试受影响范围。受影响的测试失败时，这轮按没有改善处理。
- 改动解决案例代表的那一类问题。不写识别具体评测案例的特判。

评测规则：

- 只新增在当前代码上失败的案例。不删除、不修改已有案例。
- 新增后在当前代码上重测，结果成为新的比较基准。记录新增前后的两个结果。达标线不变。

`/first-principles` 的目标和成功标准取自目标约定。它得出的结论在授权范围内直接执行，不停下等用户确认。

下列情况结束循环，进入第 4 步：

- 评测结果达标。
- 轮数达到预算。
- 连续三次代码改动都没有改善。

下一步超出授权范围时，停下问用户这一件事。得到答复后，把答复写入约定的授权范围，继续循环。

完成条件：出现上面三种情况之一；每一轮都有进展记录。

## 4. 验收

有保留的改动时，通过 Skill 工具加载 `/diff-review`，审查基线 SHA 之后的改动。修复审查发现的问题后重跑评测，结果写入进展记录。

按下面的格式请用户验收，停下等待：

1. **结果**：基线和最终的评测结果，是否达标；评测命令，用户可以自己重跑。没达标时写明差多少、卡在哪。
2. **走过的路**：每轮一句话，说明试了什么、有效还是被撤回。
3. **代理替你定了什么**：按推荐自行决定的事项，每项一句理由和怎么改回。
4. **没验证的和风险**：本轮没有运行过的检查不说通过。需要用户参与才能继续的方向写成建议，例如用 `/trial` 比较两个方案、用 `/ablation` 确认各项改动的贡献。

验收单写给没看过代码的人：一句话说一件事，不用函数名、文件名或内部编号代替说明。项目 `AGENTS.md` 写了试用方式的，附上试用命令。

验收通过后，合入、推送和部署按用户的指示和项目规则做；推送用 `/safe-push`。验收不通过时，把用户的意见写入约定，轮数重新从 0 计，回到第 3 步。
