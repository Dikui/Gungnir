# 选择技能

帮助选择下一步，不要求记住全部技能。下列流程说明技能如何配合。改代码的任务默认走 `/implement`；其余情况按下表推荐，由用户决定是否调用。

## 从想法到实现

1. **明确想法**：用 `/grill-me` 访谈。在项目仓库中，它同时将术语和决策保存到 `GLOSSARY.md`、ADR。它使用 `/grilling` 的访谈方式。
   访谈中怀疑方向本身有问题时，可先用 `/first-principles`。
2. **需要原型时验证**：状态、业务逻辑或界面问题无法只靠对话解决时，用 `/handoff` 导出上下文，在原型目录的新会话中使用 `/prototype`。完成后再用 `/handoff` 将结论带回原对话。
3. **按规模实施**：
   - 一次会话能完成：在当前上下文使用 `/implement`。
   - 需要多次会话：先用 `/to-spec` 整理需求。想先审一遍需求漏洞时，可用 `/adversarial-review` 审查需求文档；需求或方案明显膨胀时，可用 `/occams-razor` 检查方案组成的依据。再用 `/to-tickets` 拆成可贯通各层、独立验证的任务，并声明前置依赖。随后用 `/implement` 处理整个任务单目录：它按依赖分批，同批任务各派一个子代理在独立 worktree 中并行开发，再逐个合并。本地任务存入 `.scratch/<feature>/issues/` 的独立文件；远程 tracker 使用原生依赖链接。任务须自包含，子代理只读取对应任务单。

`/implement` 会自行加载 `/tdd`、`/local-test` 和 `/diff-review`：一次完成一个“失败测试 → 最小实现”循环，再只测试受影响范围并沉淀值得保留的测试，最后分别审查编码规范和需求符合性，然后请用户验收。不必另外指定这三个技能。

实现中加入多项优化、需要确认哪个起作用时，可用 `/ablation`。

需要撰写 PR 正文时，可显式指定 `/pr-body`，用最小图示、前后验证证据、可回退性和影响范围说明变更。`/implement` 验收通过后会自行用 `/safe-push` 推送。单独提交或推送时，说“提交”“推送”即可使用 `/safe-push`：它检查不应入库的内容，只在有阻断或待决定项时停下；它不写 PR 正文。

4. **复盘工作环境**：构建结束后，可用 `/retro` 回顾会话。它按严重程度提出导航、自动检查、编码规范、规则文件和工具改进。机器可判断的问题交给确定性检查，需要判断的问题交给编码规范。

只需在没有完整需求文档时用测试驱动一个具体行为，可单独选择 `/tdd`。按指定基准审查分支或 PR，可单独选择 `/diff-review`。

### 保持上下文连续

从访谈到 `/to-tickets` 保留同一上下文，不中途清空或压缩，确保它们基于同一组讨论。之后由 `/implement` 为每张任务单派独立上下文的子代理，子代理只读取对应任务单。需要复盘时，在清空上下文前运行 `/retro`；已经清空时，提供原会话日志的位置。

若在拆分任务前已接近约 150k token 的 smart zone 参考范围，则在最近的阶段结束处用 `/compact`，再继续。不要硬撑已经退化的上下文。

## 其他起点

| 情况 | 推荐流程 |
| --- | --- |
| 外部缺陷报告或功能请求积压 | `/triage` 分类和验证，形成可交给代理的任务，并在简报中写明后续技能：`/implement`、`/diagnosing-bugs`、`/to-spec` 或 `/trial`。它不处理你自己创建的任务；`/to-tickets` 的产物已可执行，无需再次分流。 |
| 难以定位、偶发或回归缺陷 | `/diagnosing-bugs` 先建立能复现该缺陷的检查命令，再验证原因并修复。修复后可在同一会话显式调用 `/retro`，检查什么措施本可预防缺陷；若发现缺少可测试的 seam，再考虑 `/improve-codebase-architecture`。 |
| 一次会话无法规划清楚的大任务 | `/wayfinder` 适合从 0 设计的较大开发，会先分析方向，再在 tracker 中建立决策地图，逐项解决问题，直到路径明确。它较重，不用于范围明确的功能。 |

`/wayfinder` 默认产出决策，不直接实现。地图清楚后，先用 `/to-spec` 收拢相互关联的决策，再进入 `/to-tickets` 和 `/implement`。只有最终发现任务很小时，才直接进入 `/implement`。

## 遇到问题时选方法

遇到下列情况时，推荐对应技能，由用户调用。

| 触发信号 | 技能 | 调用前准备 |
| --- | --- | --- |
| 怀疑解决方向选错，方案主要依赖“大家都这样做” | `/first-principles` | 当前方案 |
| 想找出计划、需求或代码的反例 | `/adversarial-review` | 审查对象；代码需提供基准 |
| 方案越来越复杂，说不清每个部分为什么存在 | `/occams-razor` | 需求文档或需求清单 |
| 需要在真实后端代码中比较几种实现（布局、分配、锁、吞吐等） | `/trial` | 要回答的问题、候选方案、比较指标 |
| 加了多项优化或机制，不清楚收益来自哪个 | `/ablation` | 可量化指标和可重复的测量命令 |
| 模块职责和依赖混乱，改一处牵动多处 | `/cohesion-coupling` | 要分析的模块或目录 |

- `/grill-me` 通过用户回答问题打磨方案；`/first-principles` 由代理查证前提、从头推导，给出保持、调整或换方向的结论。
- `/diff-review` 按编码规范和需求审查代码差异；`/adversarial-review` 由与作者隔离的攻击方针对主张找反例并逐条核实，也能审查计划和需求文档。
- Claude Code 自带的 `/simplify` 简化代码写法；`/occams-razor` 判断方案各组成是否有需求或证据依据。
- `/improve-codebase-architecture` 寻找可深化的模块并讨论改造方案；`/cohesion-coupling` 提供职责、依赖和共同修改的证据与重组方向，不讨论具体接口设计。
- `/diagnosing-bugs` 定位缺陷或性能回退的原因；`/ablation` 在收益已存在时测量各机制的贡献。
- `/prototype` 用临时代码验证逻辑或界面，不写测试；`/trial` 在真实代码中实现几个方案，用同一组测试和测量选出一版。

## 架构维护与术语

- `/improve-codebase-architecture`：维护时查找可深化的模块。需要先拿到职责、依赖和共同修改的证据时，先用 `/cohesion-coupling`。选中的方向回到 `/grill-me` 讨论；具体接口设计用 `/codebase-design`。
- `/domain-modeling`：术语模糊、一词多义，或有难以逆转的决策要记成 ADR 时使用。

## 阶段结束时如何继续

访谈、实现、验证等阶段之间，按 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 的决策顺序选择：

- **继续当前会话**：上下文仍有用时保留它，避免重新获取原始资料的成本。先判断这个选项。
- **`/clear`**：当前内容对下一阶段已无用时清空。
- **`/handoff`**：需要更换代理运行环境、目录、协作者，或在阶段中途分出旁支任务时，写便携 Markdown 交接文档。
- **子代理**：将范围明确的任务放入独立上下文，并取回报告。
- **`/compact`**：以上情况都不适用时，压缩当前上下文，用摘要继续。它是最后的默认选择，不是第一个选项。

在阶段边界作决定。阶段中途通常继续当前工作，或将剩余部分分给子代理。

## 可单独使用的技能

- `/mockup`：需要长期保留、随需求更新的界面设计稿时使用。用完即弃的原型选 `/prototype`。
- `/research`：需要一手来源的事实时使用。调研在后台进行，结果可带回 `/grill-me` 讨论。
- `/wait-what`：没听懂代理的解释时使用。
- `/writing-for-agents`：编写或精简技能、`AGENTS.md` 和供代理查阅的文档时使用。

## 首次配置

首次使用工程流程前，用 `/setup-dikui-skills` 配置 issue tracker、分流标签和领域文档布局。也支持自定义 tracker。
