# Gungnir 工作流

- 改代码的任务走 `/implement`，由它串起 `/tdd`、`/local-test` 和 `/diff-review`。不确定用哪个技能时，先看 `/ask-dikui`。
- 测试只跑这次改动影响的范围，按 `/local-test` 做；不运行完整测试套件。全量由仓库的 pre-push 钩子在版本号前两位变化时运行。
- 代码没有改动时，不重跑同一条测试命令。
- 被派单的执行者（任务来自任务单、卡片或派单）只按任务中的实现规则完成这一项，不再拆分任务或派单。
- 受影响测试和全量测试的命令见仓库 `AGENTS.md` 的 Testing 一节。
- 有确定答案的下一步和确认不停下来问用户：能从代码、文档、偏好或已有决定推出答案的，按推荐做，一路做到验收。只在扫描阻断、测试失败、合并冲突，或要在没有依据的选项间取舍时停下。合入默认分支、推送和部署等用户验收通过后再做；被派单的执行者不做这三件事。
- 用户偏好分两级：全局偏好（`~/.gungnir/preferences.md`）由同一个钩子附在本文末尾，项目偏好在仓库 `AGENTS.md` 的“偏好”一节，冲突时以项目为准。怎么记录见 `/grilling`。

## 验收单

请用户验收时按以下顺序写，写法同下面的“提交方案待审”：

1. 改完有什么不同：用户能看到的行为变化，附一个例子和怎么试。
2. 代理替你定了什么：按推荐自行决定的事项和新记下的偏好（注明全局或项目），每项一句理由和怎么改回。
3. 验证证据：实际运行的命令和结果、截图路径；没验证的写明。
4. 风险和未完成。

验收通过后合入默认分支、推送（视为已授权）并按项目方式部署；不通过时按意见修改，再出一份验收单，只列差异。

## 提交方案待审

向用户提交方案、设计或变更待批准时，写给没看过代码、也没跟上你思路的人。目标是用户读一遍就能决定。只改一两处的小事不用此格式，只写一句话。

按以下顺序写：

1. 结论：一句话说要做什么、为什么。
2. 改完有什么不同：写“现在……，改完……”。用户能看到的行为优先，并举一个具体例子。
3. 需要你决定：每项给推荐和不选的后果；没有就写“无需决定”。
4. 风险：写不可逆或对外的后果；没有就写“无”。
5. 依据：一两句话，分开写已验证的和推断的。

写法：

- 一句话说一件事，写明谁来做。
- 不用函数名、文件名、内部编号或你刚起的名字代替说明。必须提到时，先说它是做什么的。
- 同一个东西始终用同一个词。
- 用户决定时用不上的内容都不写，包括改动清单和实现步骤。用户要看时再给。
- 有 3 个以上相互关联的部分时，附一张图。

再次提交时，只列和上一版的差异。
