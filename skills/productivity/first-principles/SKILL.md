# 第一性原理

输入：当前方案的文字、文档、issue 或代码路径。

## 开始前

- 读取已有的 `GLOSSARY.md` 和 `docs/adr/` 中的相关 ADR。
- 把 ADR 中记录的决策和理由作为证据。
- 只给诊断结论和建议。
- 不修改任何文件。
- 展示或记录命令、输出或环境信息前，将秘密值替换为 `<REDACTED>`。

## 执行规则

- 按顺序执行步骤。
- 完成条件未满足时，不进入下一步。
- 跳过某步时说明理由。
- 需要用户确认时，提出问题。停下等待回答。收到确认前不按假设继续。
- 无法交互时，输出待确认问题和已完成的部分。以 `未完成：等待用户确认` 结束。
- 能从仓库、文档或工具查到的事实，由代理自行查证。
- 决策交由用户确认。
- 惯例不等于错误，只表示未验证。
- 证据不足的条目标为 `待确认`。写明缺少的证据。
- 在结论中写明覆盖范围和未覆盖部分。有未覆盖部分时标为 `部分完成`。
- 不得用“未发现问题”代替覆盖说明。不得据此给出整体通过结论。

## 步骤

### 1. 重述目标
用一句话写出不含实现方式的目标。写明成功标准。请用户确认目标和成功标准。
完成条件：用户确认了目标和成功标准。

### 2. 拆前提
列出方案依赖的全部前提，包括技术、需求、资源和用户行为。为每条前提编号。
将每条前提标为事实、惯例或猜测。事实附文件、数据、文档或 ADR 证据。查不到证据的标为猜测。
完成条件：每个关键决定至少对应一条前提；每条前提都有类别；事实都有证据出处。

### 3. 重新推导
不参考当前方案。只用事实和目标推导满足目标的最少必要组成。有分歧时给出两个候选。
完成条件：每个组成都能指向某条事实或目标；没有引用惯例或猜测。

### 4. 对比
逐项列出当前方案与推导方案的差异。标明每处差异来自哪条惯例或猜测。
完成条件：每处差异都有来源。

### 5. 结论
给出保持、调整或换方向的结论。选择调整时列出调整项。
写出哪条猜测被证伪会反转结论。给出最便宜的验证办法。
可建议用户调用 `/research`、`/prototype` 或 `/ablation` 验证。

## 产出模板

按以下标题和表头输出。

```
## 目标
<一句话目标>；成功标准：<…>

## 前提
| # | 前提 | 类别（事实/惯例/猜测） | 证据或说明 |

## 推导方案
<组成列表，每项注明依据的前提编号>

## 差异
| 当前方案 | 推导方案 | 差异来源（前提编号） |

## 结论
状态：完成 / 部分完成；覆盖范围：<…>；未覆盖：<…>
保持 / 调整 / 换方向：<…>
反转条件：前提 #<n> 被证伪时 <…>；验证办法：<…>
```
