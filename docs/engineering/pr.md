## 功能

`pr` 定义 pull request 正文的形式：用 **Summary** 展示变更，用 **Evidence** 证明有效，用 **Merge Danger** 判断合并风险。它是格式参考，不是工作流。它不会推送分支、创建 PR 或决定 PR 的内容；它告诉[代理](https://www.aihero.dev/ai-coding-dictionary/agent)在编写正文时应采用什么形式。

摘要是一幅图示，而非一段叙述。默认 PR 正文用文字讲述 diff，这个技能则选择能说明关键点的**最小视图**（伪代码、调用树、组件树、文件树、Mermaid 图或有针对性的 diff），并保持周围文字简短。审查者已经打开 diff；正文的作用是在阅读前展示它的结构。

## 何时使用

输入 `/pr` 手动调用。代理不会因为正在编写 PR 正文就自动调用。其他技能引用也只表示流程依赖，详见[调用规则](../invocation.md)。

| 你的情况 | 使用 |
| --- | --- |
| 分支已准备好，需要便于审查者浏览的正文 | `pr` |
| 代码已写好，但尚未审查 | 先由用户调用 [code-review](https://aihero.dev/skills-code-review)，再调用 `pr` |
| PR 已创建，审查意见陆续返回 | 这套技能尚未覆盖；`pr` 只编写正文 |

## 模板

依次包含三个章节：

- **Summary**：一个或多个小图示，每个图示放在它支持的简短文字旁。通常用一个，有时用几个，很少全部使用。只保留审查者需要的调用、文件、props 和边界。
- **Evidence**：修改前后对比。变更涉及视觉效果，且[环境](https://www.aihero.dev/ai-coding-dictionary/environment)能够截图时，截图是最强证据；否则，用伪代码写出修改前失败、修改后通过的确切测试，或展示发生变化的控制台输出。
- **Merge Danger**：变更属于**单向门**还是**双向门**，以及**影响范围**。双向门返回成本低；单向门（破坏性迁移、移除公共 API、难以撤销的决策）则不然。影响范围说明变更出错时可能损坏什么，例如布局偏移、API 使用方、移动端响应式表现。

门的判断是核心。它将“合并安全吗？”从直觉变为审查者可以反驳的明确主张，也指明应将[人工审查](https://www.aihero.dev/ai-coding-dictionary/human-review)精力放在哪里：影响范围小的双向门可以快速浏览；单向门值得仔细阅读。

## 常见问题

**能相信代理自己对门的判断吗？**

不能盲信，这正是要求明确写出的原因。变更作者同时在给自己的工作评级，而自评恰好最容易说出“双向门，影响范围小”。可逆性也常常无法从 diff 看出。一位用户说：“回滚提交无法撤回一批已发出的邮件”；受功能开关控制的发布，也只有在首次按新格式写入之前才是双向门。技能提供定义（破坏性操作和难以撤销的决策属于单向门），而非检查清单，因此 Merge Danger 最值得仔细看。两件事有帮助：确保代理面前有[任务单](https://www.aihero.dev/ai-coding-dictionary/ticket)或[需求文档](https://www.aihero.dev/ai-coding-dictionary/spec)，而非只有 diff；将仓库始终视为单向门的变更（数据库结构迁移、对外发送或删除内容）写在代理判断前会读取的地方。

**它会替我创建 PR 吗？**

不会。`pr` 只覆盖正文。[implement](https://aihero.dev/skills-implement) 最后提交到当前分支。增加创建 PR 的技能或选项（如 `/to-pr`，或让 `implement` 创建 PR 而非提交）仍是待讨论的提案；一位用户的临时方案是在本地用一句指令覆盖 `implement`，让它创建 PR。[implement-spec](https://aihero.dev/skills-implement-spec) 是例外：若跟踪器通过 PR 关闭工作，或你要求 PR，它会创建草稿 PR。在本仓库中，只有你明确调用 `pr`，它才为 PR 描述提供此格式。

**它会不会又生成一大堆文字和图？**

它正是为避免这种情况设计的，但仍可能发生。用户对代理 PR 正文的抱怨很一致：“摘要很长，但我只需要知道改了什么、如何验证、什么可能出错，以及合并是否安全。”技能要求省略开场白、保持文字简短，并选择最小视图，通常一个图示，很少全部使用。若仍得到一叠图，代理就忽略了指令；若正文巨大是因为 diff 巨大，问题是 PR 的规模，`pr` 不会帮你拆分。

**仓库已有 PR 模板，哪个优先？**

默认没有优先级：`pr` 自带模板，不会查找 `.github/pull_request_template.md` 或类似文件。多位用户要求技能遵循仓库模板；若不处理，代理会收到针对同一文档的两套竞争指令。请在仓库的代理文档中明确，例如填写仓库模板，再在其中加入 Summary、Evidence 和 Merge Danger。

**输出是 HTML 吗？为什么 Mermaid 图没有渲染？**

输出是 Markdown PR 正文，不是 HTML 页面。GitHub 和 GitLab 会在 PR 描述中渲染 Mermaid 块，但终端不会，因此代理在本地展示时仍是原始文本。CLI 运行环境中的用户使用 ASCII Mermaid 渲染器，或要求代理将 HTML 版本附到 PR。Mermaid 只是六种视图之一；调用树、文件树或有针对性的 diff 在各处都能直接阅读。

**它能整理返回的审查意见吗？**

不能。它写完正文就停止。用户多次提出整理其他开发者或审查机器人意见的需求（哪些值得处理，哪些不是问题），但这不是此技能的职责。

**PR 变化时，它会持续更新正文吗？**

不会。它在某个时间点编写正文，PR 在审查期间变化后，正文会过时。大幅变更后，请明确调用 `pr` 并要求代理重写正文，同样使用此格式。

**变更没有 UI，Evidence 放什么？**

除了截图之外的证据。只有视觉变更时截图才是最强证据；对于迁移、后台任务或重构，证据是修改前失败、修改后通过的确切测试，或变化的控制台输出。单说“测试通过”是一项主张，不是前后对比。

**它能标明正文由 LLM 编写吗？**

它本身不会。一位用户在仓库代理文档中设置了常驻指令：代理编写的每个 issue、评论和 PR，都以披露说明结尾。该规则属于仓库，可以覆盖代理发布的所有内容，而非只针对一种文档的模板。

## 生效标志

- 不打开 diff，仅看 Summary 图示就能知道 PR 改了什么。
- 正文没有开场白，从 Summary 标题开始。
- Evidence 展示修改前后，而非只声称测试通过。
- 每个 PR 都说明门的类型和影响范围，单向门需要仔细审查。

## 所处位置

构建结果以 pull request 发布时，`pr` 位于审查和复盘之间：`to-spec → to-tickets → implement → code-review → pr → retro`。它仅允许用户手动调用；在此流程之外编写 PR 正文，也需要明确指定 `pr`。

- [code-review](https://aihero.dev/skills-code-review) 位于它之前，因为 PR 正文应描述已经审查的 diff。
- [implement](https://aihero.dev/skills-implement) 生成正文描述的提交。

不确定当前情况适合哪个技能时，[ask-matt](https://aihero.dev/skills-ask-matt) 可帮助选择整套技能中的流程。
