## 它会做什么

`implement` 按需求文档或任务单实现功能，检查结果，审查代码，再把工作提交到当前分支。

代理尽可能在预先约定的测试边界（seam，即观察行为而不暴露内部实现的公共接口）上使用 `/tdd`。实现期间定期运行类型检查和单个测试文件，最后运行完整测试套件，并使用 `/diff-review` 审查这次工作。

## 什么时候使用

当需求已经明确、工作可以在一次会话内完成时，使用 `/implement`。输入中提供需求文档或任务单的完整引用，避免只给一个可能有歧义的编号。

由你输入 `/implement` 调用；单张任务单或小需求时，代理也会自行调用。

需要跨多次会话时，先用 `/to-spec` 和 `/to-tickets` 整理、拆分工作，再按依赖顺序逐张实施。想一次协调整份需求的任务图时，使用 `/implement-spec`。

## 交互与决定

你负责提供明确的工作范围，并在开始前确认当前分支就是希望保存实现的分支。技能要求提交到当前分支，没有创建集成分支的步骤。

使用 `/tdd` 时，代理会先列出测试边界并请你确认；未经确认的边界不写测试。需求中已由你确认的边界可作为依据。

## 如何判断它有效

- 实现能对应需求文档或任务单中的要求。
- 使用 `/tdd` 的部分先有失败测试，再有最小实现，测试只覆盖已确认的边界。
- 实现期间有类型检查和单文件测试记录，收尾有完整测试套件结果。
- 审查使用了有效的提交范围，工作最终提交到预期分支。

## 常见问题

**它与 `/tdd` 有什么区别？**

`/tdd` 规定测试写法和逐轮开发规则；`/implement` 负责把需求变成实现，并组织检查、审查和提交。只想用测试驱动一个具体行为时，可以直接调用 `/tdd`。

**它会关闭任务单或创建 PR（合并请求）吗？**

本技能没有规定这两个步骤。它明确要求的是提交到当前分支。需要协调任务完成状态和按跟踪器规则处理 PR 时，使用 `/implement-spec`。

**为什么审查看不到刚写的改动？**

`/diff-review` 只审查固定提交之间的差异，未提交改动不在范围内。`/implement` 的步骤是先审查再提交，因此需要明确哪些提交包含待审工作；差异为空时，不能把停止审查当作通过。技能没有规定如何协调这两个步骤。

**一个任务总是占满会话怎么办？**

回到 `/to-tickets` 缩小任务范围，使每张任务单能在新会话中独立完成。逐张实施时，按依赖顺序处理，任务间可用 `/clear` 清空上下文。

## 它在工作流中的位置

它承接 `/to-spec`、`/to-tickets` 或已明确的小规模需求，实施中配合 `/tdd`，收尾配合 `/diff-review`。需要复盘时，在清空上下文前由你调用 `/retro`；不确定下一步时可用 `/ask-dikui`。
