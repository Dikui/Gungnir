## 它会做什么

`pr-body` 提供便于审查的 PR（合并请求）正文格式，用最小图示说明变更，用前后对比证明效果，再说明可回退性和影响范围。

正文省略开场白，使用 `GLOSSARY.md` 中的领域用语，依次包含三个章节：

- `Summary`：选择能说明关键点的最小视图，如伪代码、调用树、组件树、文件树、Mermaid 图或有针对性的差异。把图示放在它支持的简短文字旁，只保留必要结构。
- `Evidence`：展示修改前后。视觉变更且环境支持截图时优先用截图；其他情况用同一测试失败和通过的结果，或发生变化的控制台输出。
- `Merge Danger`：用 `Door` 说明变更是单向门还是双向门，用 `Blast Radius` 说明出错时可能波及什么。

双向门表示可以返回，回滚成本低时风险较低；破坏性操作或难以撤销的决策属于单向门。影响范围可以涉及布局、使用方功能或移动端表现，不能只用“风险低”代替说明。

## 什么时候使用

由你输入 `/pr-body` 调用，代理不会自行调用。适合变更已经明确，需要编写或重写 PR 正文时使用。

它只规定正文写法，不包含推送分支、创建 PR、处理审查意见或持续更新正文的步骤。代码尚未审查时，可先调用 `/diff-review`。

## 如何判断它有效

- 正文从 `Summary` 开始，没有与变更无关的开场白。
- 不打开完整差异，也能从最小视图看出改了什么，以及关键归属、顺序或边界。
- `Evidence` 展示具体的前后变化，而非只有“测试通过”的结论。
- `Merge Danger` 写明门的类型和影响范围，判断可以被审查者核实。
- 图示和文字只保留当前变更需要的信息，不为凑齐形式使用所有视图。

## 常见问题

**没有界面变更，证据写什么？**

写同一测试在修改前失败、修改后通过的结果，或具体的控制台输出变化。截图只适用于能够说明视觉效果的变更。

**仓库已经有 PR 模板怎么办？**

技能没有规定如何查找或合并仓库模板。调用时说明需要填写的模板及约束，避免正文收到两套互相冲突的格式要求。

**能直接相信单向门或双向门的判断吗？**

仍需核实。回滚代码未必能撤回已发出的通知或恢复删除的数据；正文应让审查者看清这些后果。

**为什么图示太多，或者正文已经过时？**

技能要求选择最小视图，通常无需把所有形式都用上。变更扩大或方向改变后，重新调用 `/pr-body` 并要求重写；它不会持续追踪 PR。

## 它在工作流中的位置

实现和审查明确了最终变更后，用 `/pr-body` 整理交付说明。它与 `/implement`、`/implement-spec` 的实施流程配合，但不替代 `/diff-review`，也不代替创建 PR 的操作。需要回顾这次会话的环境问题时，再由你调用 `/retro`。
