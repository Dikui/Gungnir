## 它会做什么

`triage` 在项目任务跟踪器中分类请求、验证事实并更新处理状态。结果可以是交给代理的任务简报、向报告者提出的具体问题，或附理由关闭的请求。配置纳入外部 PR（合并请求）时，也按同一流程处理。

代理完整读取正文、评论、标签和已有分流记录，检查请求是否已实现，并查阅 `.out-of-scope/` 中的拒绝记录。缺陷按报告步骤复现；PR 检出后运行相关测试或命令。需要补齐需求时，加载 `/grilling` 和 `/domain-modeling`，同步整理领域术语、`GLOSSARY.md` 和 ADR（架构决策记录）。

## 什么时候使用

收到外部缺陷报告、功能请求，或想查看待处理请求时使用。由你输入 `/triage` 调用，代理不会自行调用；可以要求展示待办、处理指定编号或直接改状态。

它使用项目已有的跟踪器和标签映射。缺少映射时，先由你调用 `/setup-dikui-skills`。待办按未标记、`needs-triage`、报告者有新回复的 `needs-info` 分组，组内最旧优先，再由你选择。

## 这是对话，需要你做决定

常规分流先给出分类、状态和理由，等待你的指示。命中旧拒绝记录时，由你决定是否沿用；状态冲突或转换异常时，也先说明并询问。

你明确要求直接改状态时，代理说明标签、评论和关闭操作后执行，跳过访谈。未经访谈转为 `ready-for-agent` 时，会询问是否需要任务简报。

每个已分流请求恰好有一个分类（`bug` 或 `enhancement`）和一个状态，实际标签按项目映射使用：

| 状态 | 含义 |
| --- | --- |
| `needs-triage` | 等待维护者评估 |
| `needs-info` | 等待报告者补充信息，回复后回到 `needs-triage` |
| `ready-for-agent` | 信息完整，可交给代理；PR 表示继续处理现有差异 |
| `ready-for-human` | 需要人工实现；PR 表示可由人合并 |
| `wontfix` | 不处理，说明理由并关闭 |

## 如何判断它有效

- 建议有代码现状和已实现检查作为依据，验证结果区分已确认、失败和信息不足。
- 任务简报写清当前行为、期望行为、关键接口、可验证的验收条件和范围，不依赖易过时的文件路径或行号。
- 等待补充的信息具体、可执行，已解决的问题进入记录，恢复处理时不重复询问。
- 分类和状态各保留一个，发布的评论和条目均以技能规定的 AI 生成声明开头。

## 常见问题

**命中旧拒绝记录就自动关闭吗？**

不会。代理会提出建议，等待你的决定。只有被拒绝的改进请求写入 `.out-of-scope/`，每个概念一个文件；已实现的请求和被拒绝的缺陷请求不写入。

**任务简报与原始报告是什么关系？**

后续代理以任务简报为工作依据，原始报告和讨论提供背景。PR 简报说明现有差异还需完成什么。具体结构见 [AGENT-BRIEF.md](../../skills/engineering/triage/AGENT-BRIEF.md)。

**它会发现所有 PR，或自动修复缺陷吗？**

PR 是否纳入、谁算外部作者，由跟踪器配置决定；待办排除协作者正在进行的 PR，明确点名时不受作者过滤限制。它负责分流和验证，难以定位的缺陷可由你另行调用 `/diagnosing-bugs`。

## 它在工作流中的位置

它把外部请求整理为可执行任务，再进入 `/implement`。自己规划的工作走 `/grill-with-docs`、`/to-spec`、`/to-tickets`；后两者的产物已可供代理使用，无需再次分流。
