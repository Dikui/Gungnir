## 它会做什么

`cohesion-coupling` 用职责表、依赖图和共同修改记录，诊断模块的内聚与耦合问题。输入是你指定的 module 或目录。

代理先确定范围，逐个写明职责，再分析 import 和调用关系、最近 200 个提交中的跨 module 同改文件对。它对照坏味道表，给出按收益和成本排序的重组方向。

## 什么时候使用

当职责和依赖混乱，或者一个改动总要修改多个 module 时，调用 `/cohesion-coupling` 并附上范围。

这是只由用户显式调用的入口技能。代理不会在普通对话中自行调用。

## 这是对话，需要你做决定

代理负责查询能从仓库、文档或工具查到的事实。未指定范围时，它会用 `git log` 找改动最频繁的区域，请你确认。重组取舍由你决定。

需要确认时，代理会停下等待。无法交互时，它会列出待确认问题和已完成的部分，并以 `未完成：等待用户确认` 结束。

## 哪些问题需要验证

职责描述、依赖关系和共同修改都是线索，以证据为准。共同修改但无显式依赖可能说明隐性耦合，仍需结合代码和相关 ADR 判断。

坏味道用“可能存在”措辞。证据不足的条目标为 `待确认`，并说明缺少什么证据。没有现成的依赖分析工具时，用 grep 估算并注明精度。

## 如何判断它有效

- 范围已确定，每个 module 都有职责描述或无法描述的原因。
- 依赖分析写明工具或方法及精度，问题附文件和 import 行等证据。
- 变更耦合给出统计命令、同改次数和是否有显式依赖。
- 建议按收益和成本排序，报告写明覆盖范围和未覆盖部分。

## 常见问题

**它与 `improve-codebase-architecture` 有什么区别？**

`improve-codebase-architecture` 寻找可改造成深模块的位置，生成报告并与用户讨论改造方案；本技能只提供职责、依赖和共同修改的证据与重组方向，不讨论具体 interface 设计。

**它会修改项目吗？**

不会。它只给诊断结论和建议，不修改任何文件，不安装依赖，也不修改 `package.json` 等清单文件。

**没有足够证据时还能得出结论吗？**

证据不足的条目会标为 `待确认`，并说明缺少什么证据。有未覆盖部分时，报告标为 `部分完成`，不据此给出整体通过结论。

## 它在工作流中的位置

先收集职责与耦合证据，再由你决定是否重组。不为假设中的需求拆分 module。需要设计 interface 时，可调用 `/codebase-design`。技能只推荐其他技能，不代替你调用。
