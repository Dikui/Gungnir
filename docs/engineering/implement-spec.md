## 它会做什么

`implement-spec` 接收需求文档及关联任务单，按阻塞关系调度实施子代理，把工作合并到同一个集成分支。

每个实施子代理使用独立的 worktree（同一 Git 仓库的独立工作目录）和分支，并加载 `/tdd` 实现任务。协调代理在可执行任务集合变化时派发更多任务；所有任务完成后，加载 `/diff-review` 审查集成分支，再交给一个实施子代理修复审查提出的问题。

## 什么时候使用

需求已由 `/to-spec` 和 `/to-tickets` 整理为带依赖关系的任务单，希望在一次协调会话中实施整份需求时，使用 `/implement-spec`。小规模工作或希望逐张实施时，使用 `/implement`。

由你输入 `/implement-spec` 调用，代理不会自行调用。

开始前提供需求文档、关联任务单和任务跟踪器。缺少跟踪器时，代理会提示你运行 `/setup-dikui-skills`。

## 交互与决定

你提供工作范围和任务依赖关系，并说明是否需要 PR（合并请求）。代理创建集成分支，尽可能在后台运行实施子代理，用文档、任务单、探索笔记和提交的指针传递上下文。

需要额外探索时，可先派探索子代理，把 Markdown 笔记保存到仓库外、后续子代理均可访问的目录。实施子代理开始前须基于集成分支，汇报完成前须合入集成分支的最新提交；完成的工作由合并子代理汇入集成分支。

使用 `/tdd` 时，测试边界须先获确认。可在需求文档或任务单中明确边界；没有确认时，不能因任务正在并行实施就省略这一步。

## 如何判断它有效

- 派发顺序遵守阻塞关系，已可执行的任务尽可能并行处理。
- 每个实施子代理有独立的 worktree 和分支，并加载了 `/tdd`。
- 所有任务完成后才审查集成分支，审查问题交给实施子代理修复。
- 收尾符合跟踪器的完成方式，报告集成分支，并清理全部实施子代理的 worktree。

## 常见问题

**它一定会创建 PR 吗？**

只有跟踪器通过 PR 关闭工作，或你要求 PR 时才创建。首次合并后创建草稿 PR，因为没有领先 `main` 的提交时无法创建；收尾将已有草稿 PR 标为可供审查。没有 PR 时，按跟踪器的方式完成每张任务单，并汇报集成分支。

**任务合并到集成分支就一定关闭了吗？**

不一定。PR 流程可以在 PR 合并时关闭工作；本技能将草稿 PR 标为可供审查，不负责在这一步合并 PR。协调时应区分实现已合入集成分支与跟踪器中的关闭状态。

**独立 worktree 能保证无冲突或快进合并吗？**

不能。技能要求实施子代理在汇报前同步集成分支，没有保证最终合并方式。任务可能修改同一文件；拆分时应明确共享接口和名称，把必须顺序实施的工作写成依赖关系。

**本地任务单用完后怎么处理？**

tracker 为本地 Markdown 时，功能的任务单全部关闭后，代理提示你删除 `.scratch/<feature>/`，git 历史保留。

**是否每个任务完成后都审查整份需求？**

不是。技能规定所有任务完成后审查一次集成分支，再修复提出的问题，没有规定反复运行全面审查的循环。

## 它在工作流中的位置

它承接 `/to-spec` 和 `/to-tickets` 的产物，用实施子代理协调整份需求的任务图。`/tdd` 属于各任务的实施过程，`/diff-review` 位于整份需求完成之后；结束后可由你调用 `/retro` 复盘。
