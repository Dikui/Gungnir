# 任务 003-progress：需要用户反复处理的技能，展示进度并允许提前结束

报告写入 `docs/tasks/003-progress/report.md`，第一行格式为 `session-id: <id>`。证据放在 `docs/tasks/003-progress/evidence/`。报告用中文。

## 背景

有些技能需要用户一轮一轮地回答或审阅，轮数事先不知道。目前用户看不到还剩多少，也没有说明怎样提前结束。本任务给这些技能加两项能力：

1. **展示进度**：每轮输出的最后单独一行，格式为 `已完成数/目前已知总数`，例如 `进度：2/6`。
2. **允许提前结束**：用户用自然语言表示要停（如"够了""先到这""结束吧"），代理就停下，整理已完成和未完成的部分，然后等用户确认。

涉及三处（已和用户确认范围）：

| 技能 | 反复处理的内容 | 进度的分子 / 分母 |
| --- | --- | --- |
| `grilling`（被 grill-me、grill-with-docs、triage、wayfinder、improve-codebase-architecture 加载） | 每轮回答一组问题 | 已回答的问题数 / 目前已知的问题数（已回答 + 本轮要问的 + 还在等前置条件或查询的） |
| `to-tickets` 第 3 步"请用户确认拆分" | 反复调整拆分直到批准 | 用户已确认的任务单数 / 当前拆分中的任务单总数 |
| `wayfinder` | 每次会话解决一张任务单，跨会话推进 | 已关闭的任务单数 / 地图下的任务单总数，另附 `Not yet specified` 中剩余的条目数 |

- `skills/productivity/writing-for-agents/SKILL.md` 及同目录文件：按其中要求修改技能正文
- `skills/productivity/grilling/SKILL.md`、`skills/engineering/to-tickets/SKILL.md`、`skills/engineering/wayfinder/SKILL.md`：要改的三个技能

## 要做的内容

### 1. grilling

- **进度行**：每轮问题之后，最后单独一行写进度，格式固定为 `进度：<已回答>/<目前已知>`。分母按上表的口径计算。因为回答后可能出现新问题，分母可能变大，在正文中说明这一点即可，进度行本身不用每次解释。可以在进度行末尾附一句短提示，说明随时可以结束，例如 `进度：2/6 · 想停可以直接说"先到这"`。
- **提前结束**：用户用自然语言表示要停时，不再提问，输出：
  - 已确定的决策（逐条列出）；
  - 未决的问题，每条附推荐答案，明确标为"假设，未经确认"；
  - 然后等用户确认，再采取行动（与现在"等用户确认双方达成共同理解后再行动"的规则一致）。
- 判断不清用户是不是要停时（例如只说"算了"，也可能是在否定某个选项），先问一句确认，不要自己猜。
- 正常结束的条件和流程不变。

### 2. to-tickets 第 3 步

- 每次展示拆分或调整后的拆分时，最后单独一行写 `进度：<已确认>/<总数>`。用户可以按编号逐条确认，也可以整体批准；整体批准就是全部确认。拆分调整后（合并、再拆、增删）重新计数，已确认的任务单若内容被改动，算回未确认。
- **提前结束**：用户表示要停时，列出已确认和未确认的任务单，询问是否只发布已确认的那部分。用户没有明确同意前，第 4 步一张都不发布。未确认的任务单不发布、不写入 tracker。

### 3. wayfinder

- 两种模式（从想法建立地图、继续已有地图）的会话结束时，最后单独一行写 `地图进度：<已关闭>/<任务单总数> · 待明确 <M> 项`，M 是 `Not yet specified` 中的条目数。数据来自本次会话已经读取的地图和子 issue 查询结果，不为了这一行额外逐张读取任务正文。
- 会话内的访谈走 grilling，进度和提前结束由 grilling 负责，wayfinder 不再重复规定。若会话内提前结束了访谈，未决问题按 wayfinder 现有规则处理（能说清的建任务单，说不清的放 `Not yet specified`）；如果现有规则没有覆盖这种情况，只补一句说明，不改其他流程。

### 4. 说明文章

更新 `docs/productivity/grilling.md`、`docs/engineering/to-tickets.md`、`docs/engineering/wayfinder.md`，按各文章已有的结构（"它会做什么""如何判断它有效""常见问题"等）补充进度和提前结束的说明。只改与本次功能有关的段落。其他文章（如 grill-me.md、triage.md）若有描述与新行为矛盾的句子，才修改，并在报告中列出；没有矛盾就不动。

### 写法要求

- 按 `writing-for-agents` 的要求写：短句、规则明确、不加解释性铺陈。三个 SKILL.md 各自新增的内容控制在 15 行以内。

name: grilling

加载条件：仅在其他技能的步骤要求加载本技能时继续；否则停止，并提示用户改用 `/grill-me` 或 `/grill-with-docs`。

持续访谈，直到双方达成共同理解。把议题整理成一棵 **决策树**：每项决策都分出依赖它的后续决策。

按轮次逐层处理决策树。**待问集合**包括前置条件已确定、可以直接提问且不需要猜答案的问题。每轮问完集合中的所有问题，逐题编号并附上推荐答案。等用户回答后重新计算待问集合，再开始下一轮。

每轮问题格式如下，相邻问题用水平线分隔：

```
❓ **Q1** - **<问题标题>**：<问题正文，可能有多段，包括多个选项>

➡️ <你的推荐答案>

---

❓ **Q2** - **<问题标题>**：<问题正文，可能有多段，包括多个选项>

➡️ <你的推荐答案>
```

用户的回答会改变这棵树。确定一项决策后，可能会出现新的可问问题。若某个问题依赖本轮尚未解决的问题，就留到之后的轮次。

每轮问题之后，在输出的最后单独一行写 `进度：<已回答>/<目前已知>`。
已回答数是用户已回答的问题数。目前已知数是已回答、本轮要问、仍在等前置条件或查询的问题数之和。新问题出现时，分母可能变大。
进度行可附短提示，例如 `进度：2/6 · 想停可以直接说“先到这”`。

查找事实是你的工作。若待问问题需要从环境（如文件系统或工具）获取信息，派子代理查询；不要问用户你能自行查到的内容。查询未完成时，先问集合中的其他问题。正在调查的事项仍是未确定的前置条件，因此只需等待依赖它的问题。决策由用户做；逐项提问并等待回答。

用户明确表示要停（如“够了”“先到这”“结束吧”）时，结束访谈，不再提问：

1. 逐条列出已确定的决策。
2. 列出未决问题，每条附推荐答案，并标为“假设，未经确认”。
3. 等用户确认双方达成共同理解后，再采取行动。

用户是否要停不明确（如只说“算了”）时，只问一句是否结束访谈，等待回答。

待问集合为空、决策树的每个分支都已处理，且没有未说明的假设时，会话结束。等用户确认双方达成共同理解后，再采取行动。

name: wayfinder
description: 为一次会话无法规划清楚的大任务建立决策地图，逐项解决问题，直到实施路径明确。

将模糊的大任务整理成 issue tracker 中的决策地图。先明确目标，再逐项解决实施前需要决定的问题。

目标可以是需求文档、关键决策或具体变更。此流程既适用于工程任务，也适用于课程内容等其他领域。

## 工作范围

默认只做规划。每张决策任务单解决一个问题，直到实施前已无待定事项，且没有剩余任务单。此时交接给执行阶段。

如果本次任务需要包含实际交付，在地图的 `Notes` 中明确说明。否则，输出决策结果，不直接实施目标。

## 地图与任务单

**地图**是带有 `wayfinder:map` 标签的 issue，是本次规划的权威入口。每张**决策任务单**都是地图的子 issue。

地图只保存决策摘要和链接。详细答案保存在对应任务单中，不在地图中重复。向用户引用地图或任务单时，用标题作为链接文字，不单独罗列编号或 ID。

从 tracker 配置的 `Wayfinding operations` 一节读取父子关系、依赖关系和待办查询的实现方式。尚无配置时，告知用户先显式运行 `/setup-dikui-skills`。没有 tracker 时，默认使用 local-markdown tracker。

### 地图格式

每次会话先读取一次地图。未关闭任务通过子 issue 查询获取，不逐条写进地图正文。保留下列标题：

```markdown
## Destination

<用一两行说明最终要明确的需求、决策或变更。每次会话选择任务前先对齐目标。>

## Notes

<领域、本次任务需使用的技能、持续适用的偏好；如包含实际交付，在此说明。>

## Decisions so far

- [<已完成任务的标题>](link) — <一行决策摘要，详情见链接>

## Not yet specified

<目标范围内仍无法说清、暂时不能建立任务单的问题。>

## Out of scope

<明确排除的事项及原因；已有任务单时附上链接。>
```

### 任务单格式与状态

每张任务单只描述一个问题，规模应能在一次 100K token 的代理会话中处理。使用 tracker 的 issue ID 标识任务，并添加 `wayfinder:<type>` 标签。

```markdown
## Question

<本任务要解决的决策或调查问题>
```

开始任何工作前，先将任务分配给推进地图的开发者。这表示已领取，其他并发会话应跳过它。未关闭且未分配的任务才是未领取任务。

优先使用 tracker 原生依赖关系，让用户能在 tracker 界面看到可领取任务。仅在 tracker 不支持时，才在正文中记录依赖。所有前置任务都关闭后，当前任务才解除阻塞。

**可领取任务**必须同时满足：属于当前地图、未关闭、已解除阻塞、未分配。

解决后，把答案写入完成评论，再关闭任务。产物通过链接引用，不把答案或产物贴进问题正文。

### 任务类型

标签类型固定为 `research`、`prototype`、`grilling` 或 `task`。HITL 表示需要人与代理实时交流；AFK 表示代理可独立处理。HITL 任务必须由用户参与，代理不能替用户回答。

| 类型 | 参与方式 | 用途与处理方式 |
| --- | --- | --- |
| Research | AFK | 获取决策所需、当前工作目录以外的事实，如文档、第三方 API 或知识库信息。交给 `/research` 子代理。 |
| Prototype | HITL | 回答外观或行为问题。用提纲、草稿、桩代码等粗略产物帮助讨论；UI 或逻辑代码可使用 `/prototype`。将产物链接到任务单。 |
| Grilling | HITL | 通过对话形成决策，是默认类型。使用 `/grilling` 和 `/domain-modeling`。 |
| Task | HITL 或 AFK | 完成决策前必须做、但本身不需要调查、原型或决策的操作，如注册服务、配置权限、移动数据。代理可独立完成时用 AFK，否则给用户准确的操作清单。 |

`Task` 是默认规划流程中唯一执行实际操作的类型，目的是解除决策阻塞。完成后记录做了什么，以及后续任务所需的凭证位置、新 URL、行数等事实。

## 区分待明确问题与范围外事项

地图可以不完整。只为当前能说清的问题建立任务单，不提前猜测全部后续工作。

- **能说清问题**：建立任务单，即使当前还不知道答案，或仍被其他任务阻塞。
- **还说不清问题**：放入 `Not yet specified`。记录大致方向即可，不必预先切成任务大小。后续可能拆出多张任务单，也可能不再需要任务。
- **超出目标范围**：放入 `Out of scope`。它不会随规划推进自动变成任务；重新纳入时，应重新定义目标并开始新的规划。

`Not yet specified` 只保留目标范围内尚不明确的内容，排除已有决策、已有任务单和范围外事项。

发现已有任务超出范围时，关闭它。在 `Out of scope` 中记录摘要、排除原因和任务链接，不计入 `Decisions so far`。

## 使用方式

每次会话最多解决一张任务单，`research` 任务除外。

两种模式的会话结束时，在输出的最后单独一行写 `地图进度：<已关闭>/<任务单总数> · 待明确 <M> 项`，其中 M 是 `Not yet specified` 中剩余的条目数。
按本次会话已读取的地图和子 issue 查询结果计数，并计入本次新建、关闭或删除的任务单；不为进度额外逐张读取任务正文。
访谈提前结束后，先按 `/grilling` 等用户确认，再将未决问题按“区分待明确问题与范围外事项”处理。

### 从想法建立地图

1. **明确目标**：使用 `/grilling` 和 `/domain-modeling`，确定要得到的需求文档、决策或变更。目标决定范围。
2. **找出待定问题**：继续访谈，先覆盖各个方向，不深入单一问题。识别当前能开始的任务。如果路径已经清楚、一次会话就能处理完，则不建立地图；停止并询问用户如何继续。
3. **建立地图**：添加 `wayfinder:map` 标签，填写 `Destination` 和 `Notes`。`Decisions so far` 留空，把尚不明确的问题放入 `Not yet specified`。
4. **建立任务单**：将能说清的问题建为子 issue。等所有任务获得 ID 后，再建立依赖关系。暂时说不清的问题继续留在 `Not yet specified`。
5. **启动调研**：对每张新建的 `research` 任务单，并行启动一个 `/research` 子代理。结果保存在临时使用的 `research/<name>` 分支中，并从任务单链接到结果。
6. **停止**：建立地图占一次会话，本次不再手动解决其他任务单。

### 继续已有地图

用户提供地图 URL 或编号，也可以指定任务单。

1. **读取地图**：先了解全局摘要，不一次读取所有任务正文。
2. **领取任务**：用户指定时使用指定任务；否则按顺序选择第一张可领取任务。开始工作前先分配给推进地图的开发者。
3. **解决问题**：仅在需要时读取相关任务或已关闭任务的完整内容。使用 `Notes` 中列出的技能；不确定采用哪种方式时，使用 `/grilling` 和 `/domain-modeling`。
4. **记录结果**：发布完成评论，关闭任务，在 `Decisions so far` 中增加摘要和链接。
5. **更新地图**：将新近明确的问题建为任务单，再建立依赖。从 `Not yet specified` 中移除已转为任务的内容，避免重复。若发现当前任务或其他任务超出范围，按范围外事项处理。若本次决策使其他任务失效，更新或删除那些任务。

用户可能同时处理多个已解除阻塞的任务。操作 tracker 时，应考虑其他会话也在更新它。

## 它会做什么

`grilling` 提供共用的访谈方法，围绕计划、决策或想法持续提问，直到双方达成共同理解。

代理把议题整理成决策树：一项决策下面是依赖它的后续决策。前置条件已经确定、能够直接提问且无需猜答案的问题，组成当前的待问集合。

每轮问完待问集合中的所有问题。每题以 `❓`、编号和标题开头，推荐答案单独放在 `➡️` 后面，相邻问题用水平线分隔。你回答后，代理重新计算待问集合，再开始下一轮。

每轮问题之后，输出最后单独一行显示 `进度：<已回答>/<目前已知>`。分母包括已回答、本轮要问、仍在等前置条件或查询的问题；新问题出现时，分母可能变大。进度行可以附上随时结束的短提示。

## 什么时候使用

不能直接调用，由 `/grill-me`、`/grill-with-docs` 等技能加载。没有其他技能要求加载时，代理应停止并提示你改用这两个入口。完整层级见[调用规则](../invocation.md)。

只需访谈时选择 `/grill-me`；需要同时维护领域文档时选择 `/grill-with-docs`。

## 这是对话，需要你做决定

查找事实由代理负责。问题依赖文件系统或工具中的信息时，它会派子代理查询，不会把能够自行查到的问题交给你。

查询未完成时，代理先问其他已具备前提的问题，只有依赖查询结果的问题需要等待。决策由你做，代理必须逐项提问并等你回答。

待问集合为空、每个分支都已处理且没有未说明的假设时，访谈可以结束。代理仍须等你确认双方达成共同理解后，再采取行动。

你也可以说“够了”“先到这”或“结束吧”。代理会停止提问，逐条列出已确定的决策和未决问题。每个未决问题都附推荐答案，并标为“假设，未经确认”。代理等你确认共同理解后，再采取行动。

## 如何判断它有效

- 问题逐题编号，每题有单独的推荐答案。
- 本轮问题不依赖本轮尚未确定的答案。
- 回答会改变后续问题，而不是沿用预先写好的问卷。
- 查询事实不阻塞其他已具备前提的问题，代理也不替你做决策。
- 正常结束时满足原有结束条件，行动前取得你的共同理解确认。
- 每轮问题后有独立的进度行，等待前置条件或查询的问题也计入分母。
- 提前结束时，已确定的决策与未经确认的假设分别列出，行动前仍等待确认。

## 常见问题

**只说“算了”会结束访谈吗？**

如果无法判断你是要停，还是在否定某个选项，代理只问一句是否结束访谈，并等待回答。

**为什么不一次只问一个问题？**

当前方法按轮次问完所有已具备前提的问题。依赖本轮答案的问题留到下一轮，避免在前提未定时要求你猜测。

**推荐答案就是最终决定吗？**

不是。推荐供你比较和取舍，代理必须等你回答。你可以按编号选择、反对或补充条件。

**同一轮里出现了相互依赖的问题怎么办？**

指出依赖关系，让代理把依赖未定答案的问题留到后续轮次。它需要按你的回答重新计算待问集合。

## 它在工作流中的位置

它是基础技能，集中维护访谈方式。除两个访谈入口外，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 也会按各自步骤加载它。

它负责把决策问清楚；领域术语和重要架构决策的记录由 `/domain-modeling` 提供。

## 它会做什么

`wayfinder` 把一次会话无法规划清楚的大任务整理成任务跟踪工具中的决策地图，逐项解决实施前的待定问题，直到路径明确。

地图是带 `wayfinder:map` 标签的问题单，决策任务单是它的子问题单。地图只保存摘要和链接，详细答案写在对应任务单中；每次会话先读地图，再按需读取相关任务。

地图用 `Destination` 明确目标，用 `Notes` 记录持续适用的约定，用 `Decisions so far` 索引已完成决策。暂时说不清的问题放入 `Not yet specified`，范围外事项放入 `Out of scope`。

建图和继续已有地图的会话结束时，输出最后单独一行显示 `地图进度：<已关闭>/<任务单总数> · 待明确 <M> 项`。M 是 `Not yet specified` 中剩余的条目数。计数使用本次已读取的地图和子任务查询结果，并计入本次任务变动；代理不为进度额外逐张读取任务正文。

## 什么时候使用

当任务需要多次会话，且通往目标的路线仍不清楚时，由你输入 `/wayfinder` 调用，代理不会自行调用。

你可以提供一个想法，也可以提供已有地图的地址、编号或指定任务单。若初步访谈发现路径已清楚、一次会话就能完成，代理不建立地图，而是停止并询问你如何继续。

## 这是对话，需要你做决定

代理先通过 `/grilling` 和 `/domain-modeling` 与你明确目标，只为当前能说清的问题建立任务单。任务分为四类：

- `grilling`：通过实时对话形成决策，是默认类型；代理不能替你回答。
- `prototype`：用粗略产物讨论外观或行为，需要你参与；界面或逻辑代码可用 `/prototype`。
- `research`：获取当前工作目录以外的事实，交给 `/research` 子代理独立处理。
- `task`：执行解除决策阻塞所需的操作；代理不能独立完成时，给你准确的操作清单。

建图占一次会话，不再手动解决其他任务；新建的 `research` 任务会并行启动子代理，结果保存在临时使用的 `research/<name>` 分支，并从任务单链接到结果。继续地图时，每次会话最多解决一张任务单，调研任务除外。

开始工作前先分配任务给推进地图的开发者，其他会话跳过已分配任务。属于当前地图、未关闭、未分配且所有前置任务均已关闭的任务，才可领取。

会话内访谈的进度和提前结束方式见 [grilling](../productivity/grilling.md)。提前结束后，代理先等你确认整理结果，再按地图规则处理未决问题。

## 如何判断它有效

- 目标先于任务确定，每张任务单只描述一个能在一次会话中处理的问题。
- 能说清的问题成为任务单，暂时说不清的问题保留在 `Not yet specified`。
- 任务完成后有完成评论，任务已关闭，地图只新增摘要和链接。
- 新问题转成任务后从 `Not yet specified` 移除；失效任务被更新或删除。
- 范围外任务被关闭并记入 `Out of scope`，不算已完成决策。
- 会话末尾显示地图进度和待明确条目数，计数包含本次任务变动。

## 常见问题

**访谈提前结束，未决问题放在哪里？**

确认整理结果后，能说清的问题建为任务单；仍说不清的问题放入 `Not yet specified`。超出目标范围的事项仍放入 `Out of scope`。

**它会直接实现目标吗？**

默认只做规划，直到实施前无待定事项且无剩余任务，再交接执行。需要包含实际交付时，必须在地图的 `Notes` 中明确说明。默认规划流程中的 `task` 可以执行实际操作，但用途是解除决策阻塞。

**必须使用某个任务跟踪工具吗？**

它读取配置中的 `Wayfinding operations`，使用其中的父子关系、依赖和待办查询方式。尚无配置时提示你显式调用 `/setup-dikui-skills`；没有任务跟踪工具时默认使用 `local-markdown`。依赖优先用原生关系表示，不支持时才写入正文。

**它与 `/grill-with-docs` 有什么区别？**

`/grill-with-docs` 适合一次会话中的方案访谈；本技能用地图承接多次会话中的待定问题。决策任务单解决问题，不等同于实现任务单。

## 它在工作流中的位置

地图清楚后，由你调用 `/to-spec` 收拢相互关联的决策，再用 `/to-tickets` 拆出实现任务并进入 `/implement`。只有最终发现任务很小时，才直接进入 `/implement`。
